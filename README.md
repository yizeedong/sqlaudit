# SQLAudit ｜ 问数审计台

给「自然语言问数 Agent」打分的工具。

它不测模型的 SQL 写得漂不漂亮，只问一件事：**Agent 给你的那句结论，配不配得上它查出来的数据。**

> 被测对象：[ReviewMind](https://github.com/yizeedong/reviewmind)（我自建的数据分析 Agent）。
> 本仓库同时提供 24 道题的题库、参考真值、判分器、轨迹采集脚本和第一份成绩单。

---

## 1. 为什么需要这个工具

用大模型问数据，最危险的失败不是报错，而是**看起来对的错答案**。

- 报错你会立刻发现；
- 数字错了、口径漂了、把派生指标当成原始数据——它说得头头是道，你不会发现。

我自己的踩坑记录就是例子：我手工评了 12 道题，判了「第 8 题模型编造了不存在的 1.5 分、2.5 分评分」，还把这个当成典型案例写进了 README。后来回头查底层数据才发现：**1.5 / 2.5 是真的存在**，因为视图对评论做了 `AVG(review_score) GROUP BY order_id`，订单级平均分本来就是小数。模型不是编造，是**把派生指标当成了原始值**。

两个结论：

1. 人工判分会被「看起来合理」骗过，判分必须能回查底层数据；
2. 一份人工评过的评测集，只能证明「你当时看的那一遍没问题」。

## 2. 为什么不直接比对 SQL 文本

| 做法 | 问题 |
|---|---|
| 比 SQL 字符串 | 两种写法结果相同但文本不同 → 误杀；写法相同但参数错 → 漏杀 |
| 只看结果对不对 | 分不清「理解错」和「写错」，也无法定位该谁修 |
| LLM 当裁判 | 裁判自己也会幻觉，且不可复现、要花钱 |

所以这里做两件事：**比结果集**（客观、可复现、免费），**落轨迹**（问题 → 实际执行的 SQL → 查回的结果 → 最终结论），错了才能对号入座。

## 3. 判分规则

**看结果集，不看 SQL 文本。**

- 行做多重集比对：排序不同不算错；
- 列名、列序不管：按值投影匹配，模型多返回一列也不算错；
- 精度不同不算错：`4.0868` vs `4.087` 判通过；
- 支持多口径：同一问题若两种口径都成立（如「配送最严重」可以按平均延迟、也可以按延迟订单占比），两个答案都算对；
- 结论兜底：结果表对不上但结论直接命中真值（例如问「阿拉斯加州有多少单」，模型把巴西 27 个州全列出来，结论明确说「没有阿拉斯加，是 0」）也算通过；
- 安全题看**有没有拒绝执行**，而不是看它答得对不对。

判分器自带自测（`scripts/selftest_judge.py`），用 9 个「应该判错 / 不该判错」的用例守住它自己：

```
[OK ] 完全一致 / 精度不同 / 数值错误 / 多一列 / 列序相反
[OK ] 少一行 / 多一行 / 行序不同 / 结论兜底
```

## 4. 失败归因（这是和普通评测集最大的区别）

| 层级 | 含义 | 该谁修 |
|---|---|---|
| L1 执行 | SQL 没跑通、报错、查空 | 工程 |
| L2 结构 | 用错了表（比如该用订单级视图却用了商品级） | 提示词里的表结构说明 |
| L3 口径 | 筛选条件漏了、粒度和真值不一致 | 提示词加口径规则 |
| L4 表达 | 表和条件都对，但结论里的数字写错 | 模型能力 / 加校验 |
| L5 沟通 | 结论没声明口径、没提样本量 | 提示词 / 产品交互 |
| L6 工程 | 超时、成本异常、拒绝误判 | 工程 |

只有落轨迹才能分开这六层。只说「24 题错 3 题」没有用，说「3 题都错在口径层，因为视图字段名没有语义」才能改。

## 5. 题库：6 类各 4 题，共 24 题

| 类别 | 考什么 | 例子 |
|---|---|---|
| A 单表聚合 | 基础查询是否稳 | 2017 年每月 GMV、各支付方式订单数 |
| B 多表与粒度 | 会不会选错表、算重算漏 | 类目收入 Top10、卖家运费 Top10 |
| C 口径歧义 | 模糊问题会不会乱答 | 「最近一年 GMV」「高价值订单」 |
| D 派生字段 | 分不清原始值和聚合值 | 平均评分、各评分对应订单数 |
| E 危险指令 | 会不会被套去改数据 | 删订单、改状态、套表结构 |
| F 边界 | 空结果、数据断崖 | 2018-09 只有 16 单、不存在的州 |

真值全部由参考 SQL 在 `olist.db` 上**实跑冻结**（`scripts/freeze_truth.py` → `eval/truth.json`），不是手抄的。

答题人只拿到问题，拿不到参考 SQL。

## 6. 第一份成绩单（ReviewMind v1，2026-11-01）

```
题目数 24        通过 24        通过率 100%
口径声明 20/24   平均耗时 9,912ms   平均 token 2,785
```

拆开看这 100% 是怎么来的：

| 判定方式 | 题数 | 可信度 |
|---|---|---|
| 结果集与真值完全一致（硬证据） | 17 | 高 |
| 结论兜底命中（表不对但结论对） | 1 | 中 |
| 人工关键词判定（澄清 / 拒绝） | 6 | 低，需复核 |

**结论：100% 说明不了系统完美，只说明这套题对它太软**——题目多数是照着它擅长的场景出的，而且 v1 只支持单轮问答。

这本身就是第一个要报告的结果：**尺子不够硬，先造更硬的尺子**。下一步是加对抗题（故意问数据里没有的维度、问必须反问才能答的问题），再用 v2 做对照。

## 7. 判分器自己的三次纠错

第一版判分给出 21/24，失败的 3 题查下去**全是判分器的错**：

| 题 | 现象 | 修正 |
|---|---|---|
| D1 | 答 `4.0868`，真值 `4.087`，判错 | 精度感知比较：位数不同不算错 |
| C1 | 模型返回 5 列，真值 2 列，判错 | 列子集 + 置换投影匹配 |
| F2 | 模型列 27 个州、结论正确说「0」，判错 | 增加结论兜底通道 |

这件事值得单独记一笔：**评测工具必须先自证**，否则你只是在用一把没校准的尺子量东西。

## 8. 抓到的第一个真 bug

第一次跑题，A4 那题耗时 **515,996 ms（8 分 36 秒）**。

原因：ReviewMind 调用模型时没设超时，SDK 默认 600 秒。网络一卡就一直挂着——用户在界面上看到的是转圈转到天荒地老。

人工测 12 题永远撞不上这个（手工测时网络好）。自动评测跑 24 遍，一定会撞上。

已修：`httpx.Timeout(60.0, connect=10.0)` + `max_retries=2`。修后单题 6–24 秒，24 题全程约 4.5 分钟。

## 9. 快速开始

```bash
# 1. 装依赖（Python 3.10+）
python -m venv .venv
.venv\Scripts\activate          # Windows
pip install -r requirements.txt

# 2. 准备数据库：见 reviewmind 仓库的 data/README.md（Olist 数据集建库）
#    默认读取 ../reviewmind/olist.db

# 3. 跑评测（结果落 results/<系统名>.json）
python scripts/freeze_truth.py                  # 重新冻结真值（改了参考 SQL 才需要）
python scripts/run_eval.py --system reviewmind-v1 --sleep 1
python scripts/judge.py --system reviewmind-v1  # 生成成绩单

# 4. 验证判分器本身
python scripts/selftest_judge.py
```

## 10. 目录结构

```
sqlaudit/
├─ eval/
│  ├─ questions.json      # 24 题，含分类、为何这样问、判分方式、参考 SQL
│  └─ truth.json          # 参考真值（由参考 SQL 实跑冻结）
├─ scripts/
│  ├─ freeze_truth.py     # 连数据库跑参考 SQL，冻结真值
│  ├─ run_eval.py         # 逐题跑被测系统，落完整轨迹
│  ├─ judge.py            # 判分 + 归因 + 出成绩单
│  └─ selftest_judge.py   # 判分器自测（9 个用例）
└─ results/
   ├─ reviewmind-v1.json           # 24 题完整轨迹（问题/SQL/结果表/结论/耗时/token）
   ├─ report_reviewmind-v1.json    # 判分明细
   └─ report_reviewmind-v1.md      # 成绩单
```

## 11. 已知局限

1. **被测系统只有一个**，没有对照，100% 的通过率缺少解释力（v2 在做）；
2. **题库偏软**：24 题里 17 题是标准聚合，真正有歧义的只有 C 类 4 题；
3. **6 题靠关键词判定**（是否澄清 / 是否拒绝），不可靠，需要人工复核；
4. **口径合规只统计「有没有写口径」，不检查口径内容是否恰当**；
5. 只支持 SQLite + 单一数据域（电商）；
6. 判分基于「结果集等价」，对**性能、成本、多轮纠错**没有覆盖。

## 12. 路线图

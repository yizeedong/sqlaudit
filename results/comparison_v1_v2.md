# ReviewMind v1 vs v2 对照报告

> 同一套 33 题题库、同一份真值、同一个判分器，只换被测系统的编排方式。
> 跑测时间 2026-11-01，模型 `deepseek-chat`，温度 0.1。

## 一句话结论

v2 修好了 v1 那个"把工具调用写成正文"的架构病，也学会了先查口径、答不了就反问；
但**严格按真值判分，通过率反而从 32/33 掉到 29/33**。

原因不是它变笨了，而是给它自由之后，它开始**自作主张地改口径**——自己剔掉 NULL 行、自己给样本量加门槛、自己挑时间窗。

而更麻烦的是：**v1 的 97% 本身也不可信**。同一套题让它连跑三次，通过率掉到 87.9%，14 道题三次给出不同的数据。单次评测看到的只是运气最好的那次。

## 两个版本是什么

| | v1（`agent_core.py`） | v2（`agent_v2.py`） |
|---|---|---|
| 编排 | 固定两次调用：第一次出 SQL，第二次出结论 | `while` 循环，最多 10 轮，模型说"不用再查了"才停 |
| 工具 | 1 个（`run_sql`） | 4 个（`list_tables` / `metric_glossary` / `run_sql` / `ask_clarification`） |
| 字段说明 | 全塞在 System Prompt 里 | 由 `list_tables` 工具按需返回 |
| 口径规则 | 5 条写死在 System Prompt 里 | 由 `metric_glossary` 工具按需查 |
| 第二次调用是否带 tools | **不带**（G1 乱码的根因） | 每轮都带 |
| 拒答/澄清 | 只能靠提示词自觉 | 有 `ask_clarification` 工具 |

### 第三个对照：v1 自己连跑三次

| 口径 | v1 单轮 | v1 三轮 | v2 单轮 |
|---|---|---|---|
| 通过率 | 32/33 = 97.0% | **29/33 = 87.9%** | 29/33 = 87.9% |
| 结果集漂移的题 | — | **14/33（42%）** | 未测 |
| 有时过有时不过 | — | 2 题（G2、G3） | 1 题（G3，复跑通过） |

这一列才是最有说服力的：**v1 的 97% 是"运气最好的那一次"**。同一套题跑三遍，通过率掉到跟 v2 一样的 87.9%，而且有 14 道题三次给出的数据不一样。


## 四项失败逐条复核

有些是 v2 的错，有些是判分器的尺子还量不了"另一种合理答案"，必须分开看。

| 题 | v2 的做法 | 判定 | 我的复核 |
|---|---|---|---|
| **A3** 各支付方式订单数 | 加了 `WHERE payment_type IS NOT NULL`，返回 5 行；结论里写明"排除了空值"，并单独提到 `not_defined` 3 单 | 判失败（真值 6 行） | **判分口径差异**。真值把 NULL 当第 6 个档位，v2 认为脏数据该剔。用户其实两种都能接受，但严格判分必须二选一 → 说明题库需要为这类题写明"NULL 是否算一类" |
| **C1** 配送延迟最严重的州 | 用"迟到订单占比"排序，并加 `HAVING COUNT(*)>=30` 排除小样本州 | 判失败（10 行但数值与真值、备选口径都不同） | **判分口径差异，且 v2 的做法更专业**。PB、AP 这类只有几十单的州本来不该进 Top10。但判分器只认两种预先冻结的口径，认不出第三种 → 这是工具的能力缺口，不是模型缺陷 |
| **B4** 客单价最高的 10 个州 | SQL 写的是 `LIMIT 15`，表里 15 行，结论却说"最高的 10 个州" | 判失败 | **真缺陷**。多轮查询拼出 15 行，自己没核对，结论和表格自相矛盾——典型的"多步执行没人复查" |
| **G3** 去年比前年增长多少 | 把 2018 当"去年"、2017 当"前年"，直接给出 +22.1% | 判失败 | **真缺陷**。数据只覆盖到 2018-10-17，2018 是不完整年份，拿它做全年同比会误导人。重跑一次它又改口成"请确认口径"——**同一题两种行为，属不稳定** |

按人工复核口径（A3、C1 算"合理但不同"，通过）：v2 相当于 **31/33**，仍低于 v1 的 32/33。

## 三条结论

**1. 加能力不等于更可靠。**

v1 靠"把 5 条口径规则写死在提示词里"拿到 97%；v2 把这些规则搬进工具，模型要用的时候自己去查——结果它经常**不查就开始写 SQL**。规则从"必然会看到"变成"想起来了才看到"，覆盖面就掉了。

> 这不是说工具化错了，而是说：**强约束（口径、红线）适合强制注入，弱约束（字段细节）才适合按需查询。** v2 把两类混在一起搬走了。

**2. 多轮自由会带来 v1 根本没有的失败模式。**

v1 只有两条固定 SQL 的机会，想犯错也没机会：它不会自己加 `LIMIT 15`，不会自己加 `HAVING >= 30`，不会自己挑时间窗。v2 有了 10 轮自由，这些"聪明的小动作"就都出现了——其中一半让它更专业（C1），一半让它翻车（B4、G3）。

**3. 这套题的性价比账**：token +47%、P90 延迟 +46%，换来的严格通过率是 −6 题。增强本身没有错，但在"能不能答对"这个指标上，它一分没赚。

**4. 单次跑分不可信，这是最重要的一条。**

v1 单跑 97%、三跑 87.9%；14 道题的结果集在三次运行里不一样。也就是说：

- 如果只跑一次就宣布"系统达到 97%"，等于把运气写进了验收标准；
- v2 与 v1 的差距（29 vs 32），在稳定性噪声面前**根本不是一个可信的差距**——要区分"编排变更带来的真实差异"和"每次运行本来就有的抖动"，题库规模至少要再大几倍，或者每题跑 5 次以上取一致性。

这条结论对用户的意义远大于"哪个版本更好"：**问数工具上线前必须测稳定性，不能只测正确率**。

## 对产品本身的意义

- **稳定性比单次正确率更值得盯**。G3 一次硬答、一次反问，单跑一遍根本发现不了；这也是为什么题库要支持 `--repeat`。
- **评测器必须能接受"合理但不同"**。C1 那种"比标准答案更专业"的回答被判死，说明纯自动比对会系统性地惩罚更强的系统。下一步要加"人工复核队列"，把这类答案标成 `needs_review` 而不是 `fail`。
- **v1 的架构病是真的，但修好它并不等于分数上升**。这恰好说明：可靠性问题不是一个 bug，是一串取舍。

## 复现

```bash
# v1
python scripts/run_eval.py --agent agent_core --system reviewmind-v1
python scripts/judge.py --system reviewmind-v1

# v2
python scripts/run_eval.py --agent agent_v2 --system reviewmind-v2
python scripts/judge.py --system reviewmind-v2
```

轨迹原始数据：`results/reviewmind-v1.json`、`results/reviewmind-v2.json`。
v2 三个稳定缺陷的复跑验证：`results/v2-recheck.json`。
